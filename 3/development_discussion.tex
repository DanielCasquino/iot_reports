\subsection{CHECKPOINT 2: Basic Implementation with Reading}

The second checkpoint implemented a complete telemetry path from an LDR
connected to the ESP32 ADC to an MQTT subscriber. The circuit was assembled
as a voltage divider and its output was connected to GPIO35. The ESP32 was
programmed with the sketch stored in
\texttt{checkpoint2/Checkpoint2\_LDR/Checkpoint2\_LDR.ino}. The credentials
were kept in the local file \texttt{secrets\_local.h}; no credentials were
included in the shared source code.

\subsubsection{Implementation procedure}
The implementation followed these steps:
\begin{enumerate}
    \item The LDR voltage-divider output was connected to GPIO35, while the
    circuit was supplied from the ESP32-compatible voltage rail and ground.
    The fixed-resistor value and the physical orientation were recorded from
    the assembled circuit because they determine the ADC response.
    \item The ESP32 board support package and the PubSubClient library were
    enabled in Arduino IDE. The board and the serial port corresponding to
    the connected ESP32 were selected.
    \item The local Wi-Fi SSID, password, and broker address were entered in
    \texttt{secrets\_local.h}. The broker was configured on port 1883 and the
    subscriber was configured to listen to \texttt{lab/ldr}.
    \item The sketch was compiled and uploaded to the ESP32. The serial
    monitor was opened at 115200~baud to verify Wi-Fi association, display the
    assigned IP address, and observe the ADC readings.
    \item A Mosquitto subscriber was started before or during the test. The
    ESP32 then read the ADC, connected to the broker when necessary, and
    published each reading as a text payload.
    \item The illumination over the LDR was changed while the serial output
    and the MQTT subscriber were observed. This test verifies that the
    acquisition path and the publication path respond to the same physical
    stimulus.
\end{enumerate}

\subsubsection{Checkpoint validation and technical discussion}
The implementation is considered functionally validated when three
observations occur together: the serial monitor displays changing ADC
codes,
the broker accepts the ESP32 MQTT client, and the subscriber receives
payloads on \texttt{lab/ldr}. The expected payload is an integer represented
as text, because the sketch publishes
\texttt{String(valor).c\_str()}. The publication interval is approximately
one second plus the time required by ADC, Wi-Fi, and MQTT operations; it
should therefore not be reported as an exact one-second sampling period.

The reading is a raw ADC code and cannot be reported as illuminance in lux
without a sensor calibration procedure. Increasing or decreasing the code
with illumination also depends on which side of the divider contains the
LDR. This is why the circuit orientation and the observed trend must be
reported together. The implementation uses the default publish behavior of
PubSubClient, namely MQTT 3.1.1 with QoS~0. Consequently, reception of a
sample demonstrates successful best-effort delivery, but it is not a
measurement of packet-loss rate or end-to-end reliability.

The block and flow diagrams in Figs.~\ref{fig:cp2-block-diagram} and
\ref{fig:cp2-flowchart} describe the same sequence that was tested in this
checkpoint. The final report must include the corresponding serial-monitor,
subscriber, and assembled-circuit captures next to this discussion. These
captures should show the actual broker address and readings used during the
demonstration, while omitting Wi-Fi passwords and other private
credentials.

\subsection{CHECKPOINT 4: Arduino Mega + ESP32 Communication}

In this checkpoint, we implemented a small system for simulating microcontroller communication and data transmission via UART and MQTT.

After connecting the Arduino MEGA and ESP32 communication pins, we were able to transmit mock sensor data from the Arduino, receive it successfully on the ESP32, and publish to an MQTT topic, which we subscribed to from a laptop running a Mosquitto client. A voltage divider was required to avoid damaging the ESP, which runs at $3.3V$.

\subsubsection{Physical Implementation}

To enable communication between these two microcontrollers, their serial communication pins must be connected to each other. As their GND reference must also be the same, we connected their ground pins as well.

\begin{itemize}
    \item Arduino RX1: connected to ESP32 TX2
    \item Arduino TX1: connected to ESP32 RX2 (with v.divider)
    \item Arduino GND: connected to ESP32 GND
\end{itemize}

For the voltage divider, we used three $10k\Omega$ resistors to get $3.33V$ and $1.67V$. We used the first output node, as the ESP32 expects approximately $3.3V$.

The $R$ and $T$ used to name the pins stand for \textbf{receive} and \textbf{transmit}, which, despite being apparent, took us a minute to notice (sorry).

\subsubsection{Arduino Code Upload}

The Arduino Mega must mock sensor data (or simple messages) and send them via UART to the ESP32. After physically connecting the pins, we can use \textit{Serial.println()} to send a string to the ESP32. However, as the \textit{Serial} object is usually reserved for the USB connection, we used \textit{Serial1} instead. We do this on a loop with a $1000ms$ delay.

\subsubsection{ESP32 Code Upload}

The ESP32 has a more complex task. It must first connect to a WiFi network, set up an MQTT server, receive messages via UART, and publish them to an MQTT topic.

To make sure we didn't run into any issues with the WiFi network, we set up a mobile hotspot using cellular data. The SSID used was \textbf{quaso}.

In the setup function, besides initializing both the \textit{Serial} and \textit{Serial2} objects, we connect to the mobile hotspot, set up an MQTT server on port 1883 and then attempt to connect to the MQTT broker.

    \begin{figure}[htbp]
        \centering
        \includegraphics[width=1\linewidth]{img/chk4/esp_setup.png}
        \caption{ESP32 code setup}
        \label{fig:esp_setup}
    \end{figure}

After the setup, the ESP32 reads a string from RX2 and, if valid, publishes it to the MQTT topic. It does this in a loop, while also attempting to reconnect if case the connection with the broker fails.

\subsubsection{MQTT Monitoring}

After flashing both the Arduino and ESP, and succesfully setting up the config file in checkpoint 1, we ran the Mosquitto broker and, on a separate terminal session, subscribed to the MQTT topic with the following commands:

\begin{itemize}
    \item \texttt{./mosquitto -c ./mosquitto.conf -v}
    \item \texttt{./mosquitto\_sub h localhost -p 1883 -t hey/guys}
\end{itemize}

Then, we powered on both microcontrollers, and watched how the laptop received the messages sent by the ESP32.
