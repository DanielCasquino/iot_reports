\subsection{CHECKPOINT 2: Basic Implementation with Reading}

The second checkpoint implemented a complete telemetry path from an LDR
connected to the ESP32 ADC to an MQTT subscriber on another computer. The circuit was assembled
as a voltage divider, and its output was connected to GPIO35.

\subsubsection{Implementation Procedure}
The implementation followed these steps:
\begin{enumerate}

    \item The LDR voltage-divider output was connected to GPIO35, while the
    circuit was supplied from the ESP32-compatible voltage rail and ground.
    The fixed-resistor value and the physical orientation were recorded from
    the assembled circuit because they determine the ADC response.
    \item The ESP32 board support package and the PubSubClient library were
    enabled in Arduino IDE. The board and the serial port corresponding to
    the connected ESP32 were selected.
    \item The broker was configured on port 1883 and the
    subscriber was configured to listen to \texttt{lab/ldr}.
    \item The sketch was compiled and uploaded to the ESP32. The serial
    monitor was opened at 115200~baud to verify Wi-Fi association, display the
    assigned IP address, and observe the ADC readings.
    \item A Mosquitto subscriber was started before or during the test. The
    ESP32 then read the ADC, connected to the broker when necessary, and
    published each reading as a text payload.
    \item The illumination over the LDR was changed while the serial output
    and the MQTT subscriber were observed. This test verifies that the
    acquisition path and the publication path respond to the same physical
    stimulus.
\end{enumerate}


Figure~\ref{fig:2-1} shows an excerpt of the ESP32 program used for the implementation.
The code integrates the analog reading of the LDR with the Wi-Fi and MQTT communication functions.
In this way, the ESP32 is responsible for both acquiring the sensor data and publishing it to the broker,
without requiring an additional microcontroller.

\begin{figure}[htbp]

#include <WiFi.h>
#include <PubSubClient.h>
#include "secrets_local.h"

WiFiClient cliente;
PubSubClient mqtt(cliente);

// Wi-Fi and broker configuration in setup():
WiFi.begin(ssid, password);
mqtt.setServer(mqtt_broker, 1883);

// Acquisition and publication in loop():

Serial.println(valor);
mqtt.loop();
mqtt.publish("lab/ldr", String(valor).c_str());
delay(1000);
\end{verbatim}

\subsection{CHECKPOINT 3: Light-Based Blind Control with MQTT}

In this checkpoint, we implemented an automated system that responds to changes in ambient light using an ESP32, an LDR, and a potentiometer.
The LDR measures the light level, while the potentiometer establishes an adjustable threshold. 
Depending on the comparison between these values, the system controls a servomotor, a buzzer, and LED indicators.
Additionally, MQTT communication allows the servomotor to be controlled remotely through manual commands.

\subsubsection{Physical Implementation}

The system was assembled using an ESP32, an LDR with a fixed resistor, a potentiometer, an SG90 servomotor, a buzzer, three LEDs (red, green, and blue), resistors, a breadboard, and jumper wires.
The readings from the LDR and the potentiometer are compared to determine whether the measured light level exceeds the threshold selected by the user.
When the threshold is exceeded, the servomotor moves $90^\circ$ to simulate closing a blind, the red LED turns on, and the buzzer should activate as an audible warning.
Otherwise, the servomotor returns to its open position $0^\circ$, the green LED turns on, and the buzzer remains off.
The blue LED indicates the connection to the MQTT broker.

As shown in Figure~\ref{fig:chk3-1}, the red LED is illuminated while the blue LED remains on.
This is consistent with the system entering its alert state when the measured light exceeds the selected threshold.
The red LED indicates that the automatic control should close the blind, while the blue LED represents the MQTT connection status.

    \centering
    \includegraphics[width=1\linewidth]{img/chk3/1.jpg}

    \label{fig:chk3-1}
\end{figure}

In Figure~\ref{fig:chk3-2}, the green LED is illuminated instead of the red LED.
This corresponds to the normal operating state, in which the measured light does not exceed the configured threshold and the blind should remain open.
Comparing both photographs shows how the LED indicators distinguish between the two operating conditions, while the blue LED remains illuminated in both cases.

\subsubsection{Automatic Control}

To test the automatic mode, we modified the threshold using the potentiometer, covered the LDR to change the light input and observed how the system responded to the LDR reading.

As shown in the demonstrations, the system responds correctly when the potentiometer is adjusted.
When the light reading exceeds the selected threshold, the red LED turns on, the servomotor moves to the closed position, and the buzzer is expected to activate.
When the light reading is below the threshold, the green LED turns on and the servomotor returns to the open position.
This shows that the automatic control works as expected and responds to changes in the selected threshold. The sequence of sensor adjustments and actuator responses can be seen in greater detail in the automatic-control videos.

However, we noticed that the buzzer did not always sound immediately when activated.
Sometimes it started working after a while, possibly due to a loose connection, although we could not confirm this since we did not have the opportunity to test another buzzer or replace the wires.

\subsubsection{Manual Control through MQTT}

Besides automatic operation, the system also supports remote control through MQTT commands.
For this test, commands were manually published from a terminal connected to the MQTT broker, allowing us to change the servomotor position without depending on the current LDR reading.

During this demonstration, the command \texttt{cerrar} was sent to move the servomotor to the closing position, while \texttt{abrir} moved it back to the open position.
The command \texttt{auto} was then used to return the system to automatic operation, allowing the servomotor to respond again to the comparison between the LDR reading and the potentiometer threshold. These transitions can be followed in greater detail in the manual-control video.

This test is relevant because it demonstrates that the ESP32 can operate as both an MQTT publisher and subscriber. 
While the sensor measurements and system status can be published to the broker, the ESP32 can also receive commands to modify the behavior of an actuator.

\subsection{CHECKPOINT 4: Arduino Mega + ESP32 Communication}

In this checkpoint, we implemented a small system for simulating microcontroller communication and data transmission via UART and MQTT.

After connecting the Arduino MEGA and ESP32 communication pins, we were able to transmit a fixed test message from the Arduino, receive it on the ESP32, and publish it to an MQTT topic, which we subscribed to from a laptop running both the broker and a Mosquitto client. A voltage divider adapts the Mega's $5\,\mathrm{V}$ TX signal to the ESP32's $3.3\,\mathrm{V}$ logic level.

\subsubsection{Physical Implementation}

To enable communication between these two microcontrollers, their serial communication pins must be connected to each other. As their GND reference must also be the same, we connected their ground pins as well.

\begin{itemize}
    \item Arduino RX1: connected to ESP32 TX2
    \item Arduino TX1: connected to ESP32 RX2 (with v.divider)
    \item Arduino GND: connected to ESP32 GND
\end{itemize}

For the voltage divider, we used three $10\,\mathrm{k}\Omega$ resistors in series. With a $5\,\mathrm{V}$ input, the ideal node voltages relative to GND are $3.33\,\mathrm{V}$ between the first and second resistors and $1.67\,\mathrm{V}$ between the second and third resistors. In the schematic, the ESP32 RX input is connected to the first of these nodes, so the divider ratio is $20/(10+20)=2/3$. These are calculated values, not measured voltages.

    \begin{figure}[htbp]
        \centering
        \includegraphics[width=1\linewidth]{img/chk4/kicad.png}
        \caption{UART connection and voltage-divider schematic.}
        \label{fig:kicad}
    \end{figure}

The $R$ and $T$ used to name the pins stand for \textbf{receive} and \textbf{transmit}, which, despite being apparent, took us a minute to notice (sorry).

\subsubsection{Arduino Code Upload}

The Arduino Mega sketch included in \texttt{code/arduino.ino} sends a fixed test string via UART using \texttt{Serial1.println()} at 9600~baud. It uses \texttt{Serial1} rather than the USB serial interface, \texttt{Serial}. Each loop includes a 1000~ms delay; this is an application delay, not a measured transmission period.

\subsubsection{ESP32 Code Upload}

The ESP32 connects to a WiFi network, receives messages via UART, and publishes them as an MQTT client to the Mosquitto broker running on the laptop.

To make sure we didn't run into any issues with the WiFi network, we set up a mobile hotspot using cellular data. The SSID used was \textbf{quaso}.

In the setup function, besides initializing both the \textit{Serial} and \textit{Serial2} objects, we connect to the mobile hotspot, configure the destination broker address and port 1883 using \texttt{mqtt.setServer(...)} and then attempt to connect to that broker. This call configures the MQTT client; it does not start an MQTT server on the ESP32.

    \begin{figure}[htbp]
        \centering
        \includegraphics[width=1\linewidth]{img/chk4/esp_setup.png}
        \caption{ESP32 code setup}
        \label{fig:esp_setup}
    \end{figure}

After the setup, the ESP32 reads a newline-terminated string from \texttt{Serial2} and publishes non-empty messages to \texttt{hey/guys}. If the broker connection fails, the sketch retries in a blocking loop before servicing UART reception.

\subsubsection{MQTT Monitoring}

After flashing both the Arduino and ESP, and successfully setting up the config file in checkpoint 1, we ran the Mosquitto broker and, on a separate terminal session, subscribed to the MQTT topic with the following commands:

\begin{itemize}
    \item \texttt{./mosquitto -c ./mosquitto.conf -v}
    \item \texttt{./mosquitto\_sub -h localhost -p 1883 -t hey/guys}
\end{itemize}

Here, \texttt{-h} selects the broker host, \texttt{-p} its port, and \texttt{-t} the subscription topic. The use of \texttt{localhost} is appropriate because this subscriber runs on the same laptop as the broker; a subscriber on another computer must use the broker's reachable address instead.

Then, we powered on both microcontrollers, and watched how the laptop received the messages sent by the ESP32. This can be seen in the following \href{https://drive.google.com/file/d/1ZvRxRLnKPG4ej9Rm29XjDJfnk1YZ8Wml/view?usp=sharing}{demonstration video}.
